# Phase 5: architecture review (recorded 2026-10-10; findings only, nothing decided or fixed)

A senior architecture review of the design and the code, against `decisions.md`, `architecture.md` and `docs/analysis/`. Scope: unmet requirements, code that departs
from the design, weak architecture (coupling, module structure, layers), security (validation, authentication, authorization), scalability and performance, error
handling and edge cases, test gaps. Every finding names its evidence; "needs verification" marks what was not confirmed. Each fix is confirmed with the user first
(decision gate) and recorded here.

## Decisions

- 2026-10-10: Review recorded as information; no finding is accepted or scheduled yet.

## Findings

| # | Severity | Evidence | Finding | Suggested fix |
|---|---|---|---|---|
| 1 | High | `src/Identity/Application/Account/RequestAccountDeletion.php:45`; `src/Identity/Interface/Http/routes.php:44`; `src/Company/Infrastructure/CompanyServiceProvider.php:94-97` (no `UserAnonymized` listener) | A company member, **including the last company admin**, can delete their own account. This bypasses the "last company admin" rule of `RemoveMember`; memberships and job assignments keep pointing at an anonymised account and a company can be left without an admin. | Needs a design decision: refuse the deletion with 409 for the last company admin, or a Company listener that releases the membership and reassigns the jobs (as `ReassignJobsWhenMemberRemoved`). Tests. |
| 2 | High | `src/JobAlert/Application/NotifyOfLiveJob.php:40-52`; `src/JobAlert/Infrastructure/Listeners/NotifyAlertsOfLiveJob.php` | Every job that goes live runs **one search query per immediate alert on the platform**; at the target volume (200,000 job seekers × 5 alerts) one publication can mean about 1,000,000 queries in a single queued job. | Invert the match: select the alerts whose criteria fit the job in one SQL query, or split the work into one queued job per batch. |
| 3 | High | `config/queue.php:43` (`retry_after` 90); no `public int $timeout` anywhere in `src` | No job or listener sets a timeout. A job running longer than 90 s (finding 2, newsletter, erasure) is released again while still running: double execution and false retries. | A `$timeout` per long job below `retry_after`; tune `retry_after` per connection or for the `bulk` queue. |
| 4 | Medium | `src/Matching/Application/SendRecommendations.php:56-78` | About 7 queries per candidate, and `liveNear(province, 300)` is reloaded for every candidate of the same province; at 200,000 candidates more than a million queries, synchronously in the scheduler process. | Cache the pool per province within a run, load contacts, preferences and deliveries per batch, and split the run into queued batches. |
| 5 | Medium | The 11 `Erase*WhenUserAnonymized` listeners (e.g. `src/JobSeeker/Infrastructure/Listeners/EraseJobSeekerDataWhenUserAnonymized.php`) | The erasure of personal data across contexts relies only on queued listeners (3 tries), with no `failed()`, alert or reconciliation sweep. A permanent failure leaves personal data in place (data-protection risk). | A scheduled reconciliation that finds anonymised accounts whose data still exists in another context, plus `failed()` that logs or alerts. |
| 6 | Medium | `src/Shared/Infrastructure/Events/LaravelEventDispatcher.php`; dispatch after `transactions->run` (e.g. `ChangeMemberRole.php:60`) | Events are dispatched after the commit without an outbox; a crash or a failed insert into `jobs` between the commit and the dispatch loses notifications, audit entries and erasure silently. | An outbox table written in the same transaction, at least for critical events (anonymisation, security audit). |
| 7 | Medium | `src/Shared/Application/Notifications/NotificationChannel.php:9`; `src/Notification/Application/DeviceTokens/*`; `docs/handoff-history.md:315` | Requirement of `decisions.md` section 4 not met: FCM push and real-time in-app notifications. Device tokens are stored with no sender, in-app notifications are not broadcast, and `phase-5-scope.md` does not list it. | Put it in scope explicitly, or record it as deferred in `decisions.md`. |
| 8 | Medium | `src/ReferenceData/Application/Masters/MasterCatalog.php:38,40`; no tag task in any schedule | **Tag popularity** (automatic with an admin override) and **company benefit proposals** are not implemented, although `architecture.md` 2.7 and `decisions.md` section 4 require them; the column `popularity_override` is unused. | Design and code both, or record them as deferred. |
| 9 | Medium | `src/Shared/Domain/AggregateRoot.php` (3 classes use it); 72 `events->dispatch([new …])` calls in Application | Departs from `architecture.md` 2.6 ("aggregates record domain events"): events are built in the use cases, and domain events carry `ipAddress` and `userAgent` (HTTP metadata in Domain). | Record events in the aggregates of the contexts with rules (Recruitment, Company); carry the request metadata separately (an envelope or an audit context). |
| 10 | Medium | `src/JobSeeker/Infrastructure/Persistence/CompleteProfiles.php:17`, `DatabaseCandidateReader.php:73`, `DatabaseAccountPictures.php:15`; `src/Campaign/Infrastructure/Persistence/DatabaseCampaignStatistics.php:28,54` | Several cross-context table reads (`identity_users`, `recruitment_applications`) while `CLAUDE.md` names **one** exception (LegacyImport). They are documented per phase but not in one place, so an Identity schema change can break them silently. | List every exception in `architecture.md`; add a schema contract test, or replace them with a read model or view owned by Identity. |
| 11 | Medium | `src/Platform/Infrastructure/Listeners/Record*AuditEntries.php` (Platform imports 30 Company and 25 Identity classes) | The generic Platform context depends on the events of every context; each new context means a change in Platform. | An `AuditTrail` port in Shared called by each context's own listener, or an `Auditable` interface on the events. |
| 12 | Medium | `src/Recruitment/Application/ApplyToJob.php:74,79-93` | The generated CV PDF (dompdf) is built **inside the transaction** while the applicant lock is held (a long transaction); the "job is live" check runs outside the transaction (race with closing the job). | Build the PDF before the transaction; check the job status again inside it. |
| 13 | Medium | `docs/HANDOFF.md` (migration 000112 not on the real database, `CACHE_STORE` file, `CORS_ALLOWED_ORIGINS` empty, `QUEUE_CONNECTION=sync`) | The hardening is not active in the real environment yet: the rate limiter on a file cache is not atomic (throttles can be passed under concurrency), and a sync queue runs finding 2 inside the HTTP request. | A mandatory go-live deployment checklist. |

## Top three priorities

1. Finding 1: close the self-deletion of the last company admin (needs a design decision).
2. Findings 2 and 3: SQL matching for the job alert fan-out and queue timeouts, before the import and production volume.
3. Finding 5 (with 6): guarantee that the erasure of personal data completes (reconciliation or outbox), for data-protection compliance.
